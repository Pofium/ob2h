# ADR-35.1: sqlite-vec (vec0) для векторного поиска по `graph_nodes`

**Дата:** 2026-09-13 · **Фаза:** 35.1 PLAN_v1.4 · **Статус:** эксперимент проведён, флаг оставлен opt-in (`OB2H_VEC0`, дефолт off)

## Контекст

Пункт 35.1 требовал: замер p95 поиска на живой БД отдельно по `memories` и
`graph_nodes`; при p95 > 80–100 мс на ~600K векторов — эксперимент «sqlite-vec
rescore vs собственный brute force» за флагом `OB2H_VEC0=1`, критерий —
recall@10 ≥ 0.99 от brute force **и** p95 < 50 мс. Решение фиксируется цифрами
независимо от исхода.

Замер сделан на консистентной копии живой БД (`sqlite3` online-backup, 648.8 МБ,
605 415 узлов графа; копия — чтобы не накатывать миграции схемы 5→7 на живую БД).
Машина: Windows 11, release-сборка ob2h, эмбеддер — локальный Candle MiniLM (384 dim).

## Замер «до» (полный перебор, 36 golden-запросов)

| Хранилище | векторов | p50, мс | p95, мс |
|---|---|---|---|
| эмбеддинг запроса (пол) | — | 53.0 | 80.1 |
| `memories` (search_hybrid) | 284 | 64.9 | 86.4 |
| `graph_nodes` (graph.search) | 605 415 | 2049.8 | 2343.7 |

Гейт владельца (p95 > 100 мс на ~600K векторов) — **превышен**, эксперимент запущен.

## Что сделано

- `src/vector/vec0.rs`: vec0-индекс над `graph_nodes` (rowid = `graph_nodes.id`),
  два режима (`OB2H_VEC0_MODE`): **`int8`** (дефолт; в vec0 лежат те же int8-векторы
  Ф24, `distance_metric=cosine`) и `bit` (1 бит/компоненту, Hamming).
- Первый проход: `k × oversample` кандидатов (`OB2H_VEC0_OS`, дефолт 2) → рескоринг
  нашим косинусом по сохранённым векторам (полная точность, что есть в БД).
- CLI: `ob2h vec0 build|stats|recall`; поиск графа использует vec0 только при
  `OB2H_VEC0=1` и непустом индексе, иначе — прежний полный перебор.
- Регистрация расширения — `sqlite3_auto_extension` до открытия соединения
  (`Database::new`/`in_memory`). Зависимость: `sqlite-vec = "0.1.9"`.

## Замер «после» (копия той же БД)

Индекс построен: **198 941 строка** (это все узлы с непустым вектором: из 468 137
строк с `embedding IS NOT NULL` у 269 196 блоб пустой — данных для индекса нет).
Построение — 4.8 с.

| Метрика | до (brute force) | после (vec0 int8, os=2) | выигрыш |
|---|---|---|---|
| recall@10 (12 golden-запросов, ground truth = brute force) | 1.0 | **1.0000** | — |
| векторный скан, среднее, мс | 565.8 | **192.3** | **2.9×** |
| end-to-end `graph.search` p95, мс (36 запросов) | 2408.3 | **2093.4** | 1.15× |
| `memories` p95, мс | 89.5 | 85.1 (не затронуто) | — |

Ориентир §8 («rescore int8 os=2 ≈ 2.6×, recall@10 ≈ 1.0») подтверждён: 2.9× и 1.0000.

Синтетика 10K (тесты `tests/test_vec0.rs`): recall@10 — `int8` os=2/4/8 = 1.0000;
`bit` os=2 = 0.2975, os=4 = 0.4300, os=8 = 0.5375 (Hamming-проход по
неструктурированным векторам ≈ шум — bit годится только как грубый фильтр с
большим oversample). Скорость скана на 10K: 40.9 мс → 5.2 мс (7.8×).

## Почему p95 < 50 мс не достигнут (главный вывод)

End-to-end p95 упал всего на 13%, потому что векторный скан — **не** доминанта
`graph.search`. Разложение p95 до эксперимента (~2.34 с):

| Стадия | ≈ мс | Чем ограничена |
|---|---|---|
| эмбеддинг запроса | ~66 | локальная модель на CPU (Candle) |
| лексический скоринг | **~1770** | `SELECT id, label, description FROM graph_nodes` — полный скан 605K строк **на каждый запрос** |
| векторный скан | ~566 | перебор всех блобов (исправлен vec0 → 192) |

То есть узкое место — стадия 2 (полный лексический скан), а не векторный перебор.
Целевые «p95 < 50 мс» недостижимы индексацией вектора в одиночку: даже при
мгновенном векторе остаются ~1.8 с лексики + ~66 мс эмбеддинга.

## Решение

1. **Флаг `OB2H_VEC0` остаётся opt-in (дефолт off).** Критерий 35.1 выполнен
   наполовину (recall ✓ 1.0000, p95 ✗ 2093 мс), поэтому переключение дефолта на
   основании этих данных не обосновано; при этом включение безопасно (recall 1.0)
   и даёт 2.9× на векторной стадии / ~13% end-to-end.
2. **DiskANN — не нужен**: цель достигается без него (бэклог §8 закрыт).
3. **Следующий шаг для p95 (вне 35.1, отдельная задача):** лексическая стадия —
   FTS5-индекс по `label`/`description` вместо полного скана; ожидаемый эффект —
   снятие ~1.8 с из 2.34 с. p95 < 50 мс после этого упирается в эмбеддинг запроса
   (~66 мс) — его лечит кэш эмбеддингов запросов или fastembed/ort.

## Замер пары off/on на прогретой машине (финальный, тихая система)

Baseline-секция `docs/bench_baseline.md` записана из прогона OFF (flag off — дефолтный
путь). Прогретая пара на той же копии БД:

| Прогон | graph p50, мс | graph p95, мс | memories p95, мс | embed p95, мс |
|---|---|---|---|---|
| OFF (дефолт, brute force) | 1820.5 | 3432.9 | 80.2 | 70.3 |
| ON (`OB2H_VEC0=1`) | **1446.3** | **1742.4** | 71.3 | 53.3 |

Разброс между сессиями велик (холодный/тёплый страничный кэш: p95 OFF 2.3–4.9 с
в разных прогонах), поэтому смотреть надо на пары прогонов подряд: vec0 устойчиво
быстрее (p50 −20%, p95 −49% в финальной паре; направление совпадает во всех парах
серий). Итоговое решение (opt-in, см. выше) не меняется.

## Ограничения (честно)

- Инкрементальная поддержка индекса не подключена к путям записи: новые узлы
  попадают в индекс только повторным `ob2h vec0 build` (догоняет дельтами) —
  для opt-in эксперимента допустимо, для дефолта потребуется хук в upsert.
- Расход диска: int8-индекс ≈ 77 МБ на 199K векторов (385 Б/строка + чанки);
  bit-индекс ≈ 10 МБ, но с recall 0.30–0.54 на синтетике.
- Замер «до/после» — на копии живой БД (WAL-состояние снято consistent-бэкапом),
  а не на файле живой БД: миграции схемы 5→7 на живой БД не выполнялись.
