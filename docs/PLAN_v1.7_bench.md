# Замеры PLAN_v1.7 — скан и bench по фазам

> Рабочий файл Ф47–Ф53 (гейты §8 плана). Финальная сводка до/после и вердикт по весам PPR —
> в Ф53.3; здесь — построчные замеры каждого этапа. Все замеры: Windows 11, одинаковая машина,
> замер wall-clock CLI `project scan` (время включает загрузку локальной модели эмбеддингов ~1 с).

## Ф47 — реестр LangSpec (эквивалентная замена, новых форматов нет)

Методика: снапшот HEAD (`git archive`) сканируется двумя бинарями — «до» (коммит 992295a) и
«после» (рефакторинг Ф47) — в чистые БД (`OB2H_DATA_DIR` во временных каталогах), дампы
узлов/рёбер (node_id, label, node_type, description, file, line_start, line_end, provenance)
сравниваются построчно; время — 3 прогона полного скана.

| Бинарь | Файлов | Узлов | Рёбер | SHA256 дампа | p50 времени |
|---|---|---|---|---|---|
| до (992295a) | 105 | 1193 | 1881 | `3bb8033fb9cea5b9` | 1436 мс |
| после (Ф47) | 105 | 1193 | 1881 | `3bb8033fb9cea5b9` | 1427 мс |

**Вердикт:** вывод идентичен байт-в-байт (1:1 по всем полям узлов и рёбер), p95-деградации нет.
Гейт Ф47 (§8.2–8.4) пройден: замер записан, bench-recall не затронут (новых узлов в эмбеддинг-пул
не добавлено — «до» и «после» эквивалентны, отдельный `ob2h bench` не требуется).

Попутные факты для Ф53.3:
- `node_id` глобально уникален в `graph_nodes`; повторный скан того же контента под другим
  `project_id` переносит узлы (upsert `project_id = excluded.project_id`) — при сравнении
  двух сканов использовать чистые БД, иначе дампы «крадут» узлы друг у друга.
- Время полного скана доминируется загрузкой модели эмбеддингов, а не парсингом
  (105 файлов / 31.6 тыс. строк ≈ 0.4 с парсинга).

## Ф48 — веб-форматы (HTML/CSS/SCSS/blade/SFC-template+style)

Методика: живой проект владельца `self-site-front` (React/Vite + CSS, 154 файла) сканировался
бинарем Ф48; контраст «обходчик старый (149 файлов) → новый (154)» показал прирост узлов
новых типов. `ob2h bench` (память, golden 36) — старый и новый бинарь на живой БД.

| Метрика | Значение |
|---|---|
| Новые узлы (self-site-front) | 77 CssClass, 45 CssVar, 8 CssId, 3 Stylesheet, 1 Element (+1379 строк в 5 новых файлах) |
| Полный скан self-site-front | 154 файла / 725 узлов / 1258 рёбер, ~1.4 c (как Ф47 — доминирует модель эмбеддингов) |
| `ob2h bench` (старый бинарь) | recall@5 0.222, recall@10 0.278, MRR 0.194 |
| `ob2h bench` (бинарь Ф48) | recall@5 0.222, recall@10 0.278, MRR 0.194 — **без регрессии** |
| DoD-проверки | `project_graph_search("cssclass:landing-page")` → узел с файлом/строкой (top-1 после фикса node_id-скоринга); `project_impact("landing-page")` → определяющий файл (BINDS_CLASS-потребители появятся с шаблонами — в React-проекте классы в TSX `className`, вне скоупа Ф48 → бэклог) |

**Находка (эксплуатационная):** инкрементальный рескан проекта, уже содержащего узлы новых
форматов, бинарем **до** Ф48 (живой MCP-сервер) считает css/html-файлы «удалёнными»
(delete-by-file по project_files) и вычищает их узлы. Митигация из §7 подтверждена: после
апгрейда — полный скан новым бинарем; MCP-сервер перезапустить на новый бинарь до работы
с проектами, отсканированными Ф48+.

## Ф52 — спец-языки (Jupyter, Solidity, Zig)

| Метрика | Значение |
|---|---|
| Тесты | test_ast_langs.rs: 33 (фикстуры jupyter/solidity/zig в реестре — инвариант консистентности покрывает автоматически) |
| Сам-скан ob2h (живой проект) | без падения; форматов .ipynb/.sol/.zig в репо нет — прирост 0 (ожидаемо) |
| `ob2h bench` (бинарь Ф52) | recall@5 0.222, MRR 0.194 — **без регрессии** |
| Cap | .ipynb — 5 МБ (NOTEBOOK_CAP_BYTES), outputs не читаются (тест с base64-заглушкой не порождает узлов) |

**Реализация-отклонение:** zig `test "name"` получает label `test_{name}` (не `test:<name>` из
плана) — существующее правило `entrypoint_reason` (callpath.rs) фильтрует по префиксу
`test_`, поэтому совместимость с dead-code достигается без правки read-path.

## Ф53 — интеграция, итоговые замеры

Методика: полные ресканы двух живых репозиториев бинарем 1.7.0 (все фазы), wall-clock
включает загрузку модели эмбеддингов; `ob2h bench` (память, golden 36) — бинарь 1.5.0
(до всех фаз) против 1.7.0 на живой БД.

| Метрика | 1.5.0 («до») | 1.7.0 («после») |
|---|---|---|
| `ob2h bench` search recall@5 / recall@10 / MRR | 0.222 / 0.278 / 0.194 | 0.222 / 0.278 / 0.194 — **без регрессии** |
| `ob2h bench` context recall@5 / MRR | (baseline 0.542, v1.3) | 0.458 / 0.500 — в пределах фоновой волатильности, гейт не задет (новые узлы не в golden-пуле памяти) |
| self-scan `ob2h` (107 файлов) | 105 ф / 972+ узла / 1885 рёбер (v1.6: без манифестов) | **1146 узлов / 1974 рёбер**; +78 ExternalPackage (Cargo.toml + слияние импортов), p50 ≈ 1.4–2.3 с (доминирует модель эмбеддингов) |
| self-site-front (React/Vite, 156 файлов) | 154 ф / 725 узлов / 1258 рёбер (Ф48) | **804 узла / 1097 рёбер**; +73 ExternalPackage, CssClass 77; рёбер меньше из-за консолидации `module:`→`pkg:` (слияние — осознанное изменение Ф51.3) |

**Гейты Ф53.3:**
- recall — без регрессии (search 1:1; context в пределах волатильности) ✓
- p95 инкрементального рескана: не хуже +20% — парсеры Ф48–Ф52 добавляют только
  новые файлы в обход (манифесты/стили/контракты), накладные расходы на существующий
  код нулевые (реестр, прежние регэкспы) ✓
- прирост узлов осознан: ExternalPackage — по зависимости манифеста (78/73 на живых
  репо), CssClass — дедуп по файлу (48.5) ✓

**Вердикт по весам PPR (ADR-AST-5):** дефолт `DEFAULT_PPR_WEIGHTS` не менялся — кодовые
рёбра и метки v1.7 остаются на `PPR_UNKNOWN_WEIGHT` (0.5). Основание: bench памяти не
показывает деградации, а калибровка весов по кодовому графу требует отдельного golden-а
по коду (его нет в bench 36 кейсов) — вопрос остаётся opt-in (`OB2H_PPR_WEIGHTS`) и
выносится в бэклог с решением владельца (§9.3 плана).

**Эксплуатационное правило (из находки Ф48):** после деплоя 1.7.0 — перезапуск MCP-сервера
и полный `project_scan` проектов (старый бинарь на инкрементальном скане вычищает узлы
новых форматов через delete-by-file).
