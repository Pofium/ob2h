# План разработки OB2H v1.9: Безопасное хранилище секретов (Secrets Vault)

> **Версия плана:** 1.9.0 (rev.0 — черновик к утверждению)
> **Статус:** к утверждению владельцем
> **Обновлён:** 2026-10-24
> **Предыдущие этапы:** v1.8.0 (автообновление, DSH/плагин), v1.7.0 (AST-граф: веб/IaC/спец-языки)
> **Принцип совместимости:** контракт MCP расширяется **аддитивно** (36 → 41 инструмент), схема БД — только новая миграция **M8** (`CREATE TABLE` + `kv`, без изменения существующих таблиц), пути/env не ломаются, синк не затрагивается (secrets вне бандлов).

---

## 1. Мотивация

Секреты пользователя (пароли, API-ключи, токены, иные персональные значения) сегодня хранятся
в ob2h как обычные факты — либо в `memories` (`category=general/env`), либо в env-переменных,
либо в конфигах приложений. Это создаёт три конкретные проблемы:

| Проблема | Следствие сегодня | Причина |
|---|---|---|
| Секрет в памяти попадёт в recall | каждые ход LLM получает секрет в `<agent_memory>` без запроса | `build_context`/prefetch смешивают секреты с обычными фактами — признака нет |
| Секрет уезжает на VPS | копия секрета оказывается на удалённой машине | `sync` экспортирует всю таблицу `memories` (src/sync/mod.rs:213) |
| Секрет попадает в конвейеры LLM | дрим/экстракция/граф индексируют и пересказывают секрет | нет исключения для секретов из `daily`-логов/контекста |
| Нет контроля доступа | невозможно узнать, кто/когда получал значение | нет аудита и нет «запирания» |

Заказ владельца (2026-10-24): *«хранение паролей, ключей, API-ключей, различных персональных
данных… чтобы только по команде пользователя доставалась оттуда информация для действий LLM…
сам он был зашифрован пином пользователя»*.

Цель версии: отдельное, зашифрованное пином хранилище секретов с явной разблокировкой,
не пересекающееся с памятью, графом, синком и дримом; доступ к значениям — только через
специальные MCP-инструменты, работающие в разблокированной сессии.

## 2. Термины

| Термин | Определение |
|---|---|
| Пин (PIN) | секретная строка пользователя (мин. 4 символа), из которой выводится ключ шифрования. Вводится **только** локально в CLI; никогда не передаётся через MCP/LLM/чат |
| Мастер-ключ K | результат `Argon2id(pin, salt)`; живёт только в памяти процесса после unlock; на диск не пишется |
| Vault | логическая совокупность записей секретов (таблица `secrets`) |
| Unlock | состояние сервиса: K вычислен и держится в памяти, инструменты чтения/записи работают |
| Lock | состояние сервиса: K отсутствует, инструменты чтения/записи возвращают `[Error] locked` |
| Verifier | зашифрованный известный маркер, позволяющий проверить пин без хранения его хэша |
| Запись (record) | одна пара «имя → зашифрованное значение» в таблице `secrets` |

```
│   Синк (sync export) — таблицу secrets НЕ читает (ADR-21)                          │

└────────────────────────────────────────────────────────────────────────────────────┘
```

**Принципы разделения ролей:**

1. Единственный источник пина — терминал пользователя (CLI). Сервер никогда не принимает
   пин через MCP/LLM (ADR-18).
2. Инструменты чтения/записи значений требуют состояния `Unlocked`; по умолчанию vault заперт
   (при старте сервера — always locked).
3. Секреты не пересекаются с `memories`/`graph_nodes`/`daily`-логами/синком — отдельная
   таблица и явные запреты.
4. Доступ LLM к значениям — только через `secrets_get` по явной команде пользователя
   (юзер сначала разблокировал vault, затем попросил модель использовать конкретный секрет).

## 5. Функциональные требования (FR)

### FR-1. Инициализация (CLI `ob2h secrets init`)
- Создаёт vault: генерирует соль (16 байт, `getrandom`), KDF-параметры (Argon2id:
  `m=64 MiB, t=3, p=1` — дефолты), verifier-значение.
- Пин запрашивается **дважды** с `stdin` без эха; минимальная длина 4 символа; пустой пин запрещён.
- Записывает в `kv`: `secrets.initialized=1`, `secrets.salt` (hex), `secrets.kdf_params` (JSON),
  `secrets.verifier` (hex).
- Повторный init при непустом vault запрещён (или требует `--force` с подтверждением: перезапись
  невозможна без старого пина — поэтому `--force` допустим только если vault пуст / не инициализирован).

### FR-2. Unlock (CLI `ob2h secrets unlock`)
- Читает пин (без эха) → вычисляет K → расшифровывает verifier.
- Если расшифровка успешна — состояние `Unlocked{K}`, ставится deadline = now + TTL.
- Если нет — ошибка `[Error] неверный пин`, состояние остаётся `Locked`, **без раскрытия** каких-либо данных.

### FR-3. Lock
- `ob2h secrets lock` (CLI) и `secrets_lock` (MCP) — немедленный переход в `Locked` и затирание K.
- Автоматически: по истечении TTL (`OB2H_SECRETS_TTL_MIN`, дефолт 30) с момента последней активности.
- При завершении процесса сервера (drop) — затирание K.

### FR-4. Работа с записями (MCP, только `Unlocked`)
- `secrets_set(name, value, hint?)` — upsert: шифрует значение K с уникальным nonce (24 байта),
  пишет/обновляет запись. `name` — валидный идентификатор `[A-Za-z0-9._-]{1,128}`;
  `value` — строка до 64 КБ.
- `secrets_get(name)` — расшифровывает и возвращает значение; обновляет `last_accessed`/`access_count`.
- `secrets_delete(name)` — удаляет запись (физически; секреты не tombstone'ятся и не синкаются).
- `secrets_status()` — доступен всегда: `initialized`, `state (locked|unlocked)`, `ttl_left_sec`,
  `records` (число записей), `names` (список имён без значений). Имена не являются секретными
  значениями, но их выдача — сознательное решение для удобства агента (отмечено в ADR-20).
- Любой вызов `set/get/delete` в `Locked` → строка `[Error] secrets locked: запустите "ob2h secrets unlock"`.

### FR-5. Смена пина (CLI `ob2h secrets rekey`)
- Только в состоянии `Unlocked` (нужен старый K для перешифровки).
- Запрашивает новый пин (дважды, без эха) → новый K' → перешифровывает ВСЕ записи
  (расшифровать старым K, зашифровать новым K') → заменяет verifier и соль.
- Неудача/отмена на любом шаге — состояние остаётся `Unlocked` со старым K (транзакционность:
  сначала подготовить все новые ciphertext'ы в памяти, затем одним `BEGIN/COMMIT` записать).

### FR-6. Аудит
- `secrets_get`/`secrets_delete` пишут в лог уровня INFO строчку без значения:
  `secrets: get "<name>" (ok)` / `secrets: delete "<name>"` + timestamp.
- В таблице `secrets` поддерживаются `last_accessed`, `access_count`.
- Значения секретов и пин **никогда** не попадают в логи, `daily`-записи, ответы
  `secrets_status` и в `omnes_stats`.

## 6. Модель данных — миграция M8

Новая таблица + ключи `kv`. Существующие таблицы НЕ трогаются (совместимость: `memories`,
`memory_links`, `graph_*`, `ralph_*`, `projects`, `sync_state`, `kv` — без изменений).

```sql
-- M8 (v1.9): безопасное хранилище секретов.
CREATE TABLE IF NOT EXISTS secrets (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  name         TEXT UNIQUE NOT NULL,          -- идентификатор: [A-Za-z0-9._-]{1,128}
  ciphertext   BLOB NOT NULL,                 -- nonce(24) || ct || tag(16)  (XChaCha20-Poly1305)
  hint         TEXT,                          -- несекретная подсказка/комментарий
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,
  last_accessed TEXT,
  access_count  INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_secrets_name ON secrets (name);
```

Ключи `kv` (пишутся только CLI-командами init/rekey):

| Ключ | Значение |
|---|---|
| `secrets.initialized` | `1` после init |
| `secrets.salt` | hex, 16 байт |
| `secrets.kdf_params` | JSON: `{"algo":"argon2id","m":65536,"t":3,"p":1}` |
| `secrets.verifier` | hex: `nonce‖ct‖tag` расшифровки маркера `"ob2h:verify:v1"` ключом K |

`SCHEMA_VERSION`: 7 → 8; в `schema.rs` добавляется `MIGRATION_V8` и ветка
`if current_version < 8 { … }` (по образцу V2…V7).

Формат записи шифрования:

```
ciphertext = nonce (24 b) || ciphertext || tag (16 b)
  где ciphertext = XChaCha20-Poly1305_encrypt(key=K, nonce, aad=name)
```

`aad = name` связывает шифротекст с именем (подмена имени/перестановка записей ломает аутентификацию).

## 7. Ключевые сценарии (Given/When/Then)

**С-1. Жизненный цикл: init → unlock → set → get → lock**
- Given: vault не инициализирован
- When: `ob2h secrets init` (пин введён дважды)
- Then: `kv.secrets.initialized=1`, таблица `secrets` пуста, состояние `Locked`
- When: `ob2h secrets unlock` (верный пин) → `secrets_set("mail.password", "hunter2")`
- Then: запись существует, `secrets_get("mail.password")` возвращает `"hunter2"`
- When: `secrets_lock()`
- Then: `secrets_get("mail.password")` → `[Error] secrets locked: запустите "ob2h secrets unlock"`

**С-2. Неверный пин**
- Given: vault инициализирован, состояние `Locked`
- When: `ob2h secrets unlock` с неверным пином
- Then: ошибка, состояние остаётся `Locked`, никакие данные не раскрыты, `access_count` не меняется

**С-3. TTL-автозакрытие**
- Given: `OB2H_SECRETS_TTL_MIN=1`, vault unlocked
- When: проходит >60 с без обращения
- Then: состояние `Locked`, K затёрт, `secrets_get` → `[Error] locked`

**С-4. Смена пина (rekey)**
- Given: vault unlocked (старый пин)
- When: `ob2h secrets rekey`, новый пин
- Then: все ciphertext'ы перешифрованы новым K; после `lock` старый пин не открывает vault, новый — открывает

**С-5. Подмена/порча ciphertext**
- Given: unlocked
- When: `secrets_get` после изменения одного байта в `ciphertext` (внешне, через sqlite)
- Then: AEAD-аутентификация не проходит → `[Error] расшифровка не удалась (целостность)`, сервис продолжает работать, vault не сбрасывается

**С-6. Синк не содержит секретов**
- Given: в `secrets` есть записи
- When: `ob2h sync export` / `push`
- Then: в бандле нет ни одной записи из таблицы `secrets` (тест парсит бандл)

**С-7. Доступ до init**
- Given: vault не инициализирован
- When: `secrets_get` / `secrets_set`
- Then: `[Error] secrets not initialized: запустите "ob2h secrets init"`

## 8. NFR (нефункциональные требования)

| # | Требование | Критерий приёмки |
|---|---|---|
| NFR-1 | Ключ K никогда не пишется на диск | grep по коду: нет записи K в файлы/БД; только в памяти процесса |
| NFR-2 | Затирание ключа | K обёрнут в `zeroize::Zeroizing`; при lock/drop — вызов `zeroize()` |
| NFR-3 | Никакой сети/телеметрии | новые крейты — чистый локальный крипто (ADR-1/7/9 не нарушены) |
| NFR-4 | Производительность | unlock (Argon2id m=64MiB) ≤ 1.5 с на целевой машине; `secrets_get` ≤ 10 мс |
| NFR-5 | Совместимость контракта | tools/list: 36 → 41; существующие 36 инструментов не меняются; снапшот-тест обновлён |
| NFR-6 | Миграция идемпотентна | повторный запуск миграции M8 не падает; апгрейд с v1.8 (schema 7) → 8 без потерь |
| NFR-7 | Бэкапы | `omnes_backup` (VACUUM INTO) включает таблицу `secrets` (шифрованную); восстановление возможно только с пином |
| NFR-8 | Логи | в логах и `daily`-записях отсутствуют значения секретов и пин (проверка тестом на grep маркеров) |
| NFR-9 | Мультипроцессность | каждый процесс сервера разблокируется отдельно; unlock в одном процессе не влияет на другой (K — в памяти процесса) |

## 9. Решения (ADR) — продолжение нумерации PLAN.md §6

| # | Решение | Альтернатива | Обоснование |
|---|---|---|---|
| ADR-18 | Пин принимается ТОЛЬКО через CLI (`ob2h secrets …`), никогда через MCP/LLM/чат | MCP-инструмент `secrets_unlock(pin)` | пин, введённый в чате, попадает в историю сессии, `session_log` и память ob2h, виден модели — смысл шифрования теряется |
| ADR-19 | Крипто-состав: **Argon2id** (KDF) + **XChaCha20-Poly1305** (AEAD) + `zeroize` | PBKDF2-SHA256; AES-256-GCM; `ring` | Argon2id — современный memory-hard KDF (устойчив к GPU-брутфорсу); XChaCha20 — nonce 24 байта, не нужен счётчик/дисциплина nonce; pure-Rust крейты без транзитивных гигантов |
| ADR-20 | Одна таблица `secrets`; мастер-ключ K на все записи; verifier для проверки пина; `aad=name` | per-record KDF; хранение PBKDF2/argon2-hash пина | мастер-ключ упрощает rekey; verifier не хранит сырой хэш пина; aad связывает имя с шифротекстом |
| ADR-21 | Секреты НЕ синкаются (вне бандлов sync) | синк шифрованных записей | расшифровка на VPS невозможна без пина (пин не синкается), а экспорт чувствительных данных на удалённую машину — чистый риск без пользы |
| ADR-22 | Секреты недоступны конвейерам LLM (не попадают в `memories`/граф/дрим/recall); доступ — только явный вызов `secrets_*` из unlocked-сессии | «секреты как тип памяти с фильтром» | отдельная таблица + отсутствие в export/сборке контекста дают жёсткую гарантию, не зависящую от фильтров |

### Отклонённые альтернативы
- **AES-256-GCM**: требует строгой дисциплины nonce (каждый nonce уникален); при случайном
  nonce риск коллизии выше, чем у XChaCha20 (192-битный nonce). Отклонено.
- **PBKDF2-SHA256**: не memory-hard, GPU/ASIC-брутфорс пинов быстрее. Отклонено.
- **Пин через MCP (`secrets_unlock`)**: см. ADR-18. Отклонено.
- **Синк шифрованных секретов**: см. ADR-21. Отклонено.
- **Отдельный файл vault (вне ob2h.db)**: теряются атомарность, бэкапы `omnes_backup`,
  единый механизм миграций. Отклонено.
- **`ring`-крейт**: отлично аудирован, но тяжелее по зависимостям; RustCrypto-состав
  покрывает задачу. Отклонено для минимализма.

## 12. Открытые вопросы (к утверждению)

1. **Синк секретов между PC и VPS.** Нужен ли перенос секретов на VPS (в шифрованном виде,
   учитывая, что пин не синкается)? **Дефолт: нет** (ADR-21). Если да — потребуется отдельный
   дизайн транспорта ключа (не рекомендуется).
2. **Формат пина.** Допустим ли «пин = любая фраза» (≥4 символов) или строго цифровой PIN?
   **Дефолт: любая строка ≥4 символов.**
3. **Видимость имён в `secrets_status`.** Отдавать ли список имён записей в locked-состоянии?
   **Дефолт: да** (имена не секретны; удобно агенту для уточнения у пользователя).
4. **Авто-заполнение (credential autofill) из vault в интерфейсах агентов** — вне этой версии
   (бэклог). **Дефолт: да, в бэклог.**

## Приложение A. Примеры ответов инструментов

```json
// secrets_status (unlocked)
{ "initialized": true, "state": "unlocked", "ttl_left_sec": 1740,
  "records": 3, "names": ["mail.password", "github.token", "db.postgres"] }

// secrets_status (locked)
{ "initialized": true, "state": "locked", "ttl_left_sec": 0,
  "records": 3, "names": ["mail.password", "github.token", "db.postgres"] }

// secrets_get (ok)
{ "name": "mail.password", "value": "hunter2" }

// secrets_get (locked → строка ошибки)
"[Error] secrets locked: запустите \"ob2h secrets unlock\""

// secrets_set (ok)
{ "ok": true, "name": "mail.password" }
```

## Приложение B. Правила для скилла ob2h (кратко)

1. `secrets_*` — вызывать **только** по явной команде пользователя («достань пароль…»,
   «используй API-ключ…»). Не запрашивать секреты по собственной инициативе.
2. Если `secrets_status` показывает `locked` — не просить пин в чате: подсказать команду
   `ob2h secrets unlock` в терминале пользователя.
3. Полученное значение использовать только для запрошенного действия; не сохранять его в
   `memory_save`, не вставлять в текст ответа/чата без необходимости, не логировать.
4. `hint` — для несекретной подсказки (например, «почта личная»), не для значения.
